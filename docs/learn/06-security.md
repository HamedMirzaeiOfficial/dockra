# فصل ۶ — امنیت

## هدف این فصل

یاد بگیرید امنیت را با **مدل تهدید** شروع کنید، نه با فهرست ابزار؛ و ببینید هر کنترل امنیتی Dockra جواب کدام تهدید است.

## اول: از چه کسی می‌ترسیم؟

[security.md](../security.md) یک جدول دارد: داخل محدوده و بیرون از محدوده. داخل: مهاجم اینترنتی، عضو تیمی که فراتر از نقشش می‌رود، سازمان دیگر روی همان پلتفرم، باگ یک اپ. بیرون: کد عمداً بدخواه، سرور هک‌شده. این تقسیم مهم است چون بدون آن یا همه‌چیز را محافظت می‌کنید (غیرممکن) یا هیچ‌چیز را.

## مجوز در یک جا

`accounts/permissions.py::IsMember`:

```python
if request.method in ("GET", "HEAD", "OPTIONS"):
    return True
needed = getattr(view, "write_role", "developer")
return ROLE_RANK[membership.role] >= ROLE_RANK[needed]
```

و هر lookup:

```python
get_object_or_404(App, organization=request.membership.organization, slug=slug)
```

دو درس:

1. **پیش‌فرض امن**: اگر برنامه‌نویس یادش برود `write_role` بگذارد، نوشتن به developer نیاز دارد، نه هیچ‌چیز.
2. **۴۰۴ نه ۴۰۳**: برای منبع سازمان دیگر، پاسخ «پیدا نشد» است. ۴۰۳ به مهاجم می‌گوید «این شناسه وجود دارد» (enumeration). `TenantIsolationTests` همین را چک می‌کند.

## نشست‌هایی که واقعاً باطل می‌شوند

JWT بی‌حالت است؛ مشکل کلاسیکش این است که «خروج» در واقع کاری نمی‌کند و توکن تا انقضا معتبر می‌ماند. Dockra یک عدد `SessionVersion` برای هر کاربر نگه می‌دارد و آن را در claim `sv` توکن می‌گذارد (`accounts/authentication.py`). خروج، تغییر رمز، ریست رمز یا غیرفعال شدن این عدد را یکی بالا می‌برد و `VersionedJWTAuthentication` هر توکنی با `sv` قدیمی را رد می‌کند. هزینه: یک کوئری کوچک در هر درخواست. نتیجه: «از همهٔ دستگاه‌ها خارج شو» واقعاً کار می‌کند.

## محدودیت تلاش ورود و IP واقعی

۸ تلاش ناموفق در ۱۵ دقیقه برای هر IP **یا** هر نام کاربری. چرا هر دو؟ فقط IP: مهاجم از ۱۰۰ IP حدس می‌زند. فقط نام کاربری: مهاجم با یک IP حساب همه را قفل می‌کند… که البته باز هم ممکن است؛ این trade-off بین brute force و lockout است.

نکتهٔ ظریف: IP را از کجا بفهمیم؟ اگر `X-Forwarded-For` را کورکورانه قبول کنیم، مهاجم هر بار یک IP جعلی می‌فرستد و throttling بی‌اثر است. `accounts/security.py::_client_ip` فقط وقتی این هدر را قبول می‌کند که درخواست از IP خود Traefik آمده باشد (`DOCKRA_TRUSTED_PROXIES`)، که مقدار بیرونی را دور می‌ریزد.

## 2FA درست

TOTP (`accounts/security.py`) جزئیات مهمی دارد: هر کد فقط **یک بار** پذیرفته می‌شود (`last_step` ذخیره می‌شود؛ جلوی replay)، مقایسه با `hmac.compare_digest` است (زمان ثابت، جلوی timing attack)، کدهای بازیابی فقط به‌صورت هش ذخیره می‌شوند.

## رمزنگاری در حالت سکون

`config/crypto.py::EncryptedTextField` مقدار env، رمز دیتابیس‌ها، secret وبهوک و کلید TOTP را با Fernet رمز می‌کند. تست `test_secret_values_are_encrypted_at_rest` مستقیم با SQL خام می‌خواند و چک می‌کند متن ساده آن‌جا نیست. اما بدانید از چه محافظت می‌کند: از نشت فایل بکاپ دیتابیس پلتفرم. از مهاجمی که روی خود سرور است و کلید را دارد محافظت **نمی‌کند**.

env به کانتینر با `--env-file` داده می‌شود، نه `-e KEY=VALUE`؛ چون آرگومان‌ها در `ps aux` برای هر کاربر سرور دیده می‌شوند.

## SSRF: وقتی سرور شما برای مهاجم درخواست می‌فرستد

هر جا سرور به یک آدرس **از طرف کاربر** وصل می‌شود، خطر SSRF هست: کاربر آدرس `http://169.254.169.254/` (metadata ابر) یا `http://db:5432` (دیتابیس داخلی) را می‌دهد. در Dockra دو جا:

- **دانلود بکاپ از URL** (`engine/dumps.py`): فقط http/https، اسم resolve می‌شود و IP خصوصی، loopback، link-local و رزرو رد می‌شود.
- **بررسی CDN دامنه** (`apps_core/views.py::edge_server`): کاربر دامنهٔ خودش را ثبت می‌کند و رکورد A آن را هر جا می‌خواهد می‌گذارد، مثلاً `10.0.0.5`. نسخهٔ اولیه به همان IP درخواست HEAD می‌فرستاد! حالا فقط IPهای `is_global` تماس گرفته می‌شوند. این باگ هنگام آماده‌سازی همین نسخهٔ متن‌باز پیدا شد (فصل ۱۲).

## path traversal

هر جا اسم فایل از کاربر می‌آید (آرشیو آپلودی، مسیر در مدیر فایل دیسک)، باید مطمئن شد نتیجه بیرون از پوشهٔ مجاز نمی‌رود: `../../etc/passwd` یا symlinkی که به `/` اشاره می‌کند. Dockra:

- آرشیوها را با فیلتر `data` پایتون (`extractall(..., filter="data")`) و در بکاپ دیسک با `tarfile.tar_filter` باز می‌کند که لینک‌های بیرون‌رونده و فایل‌های device را رد می‌کند.
- `apps_core/extra.py::_inside` مسیر را `resolve()` می‌کند (symlinkها باز می‌شوند) و چک می‌کند ریشهٔ دیسک یکی از والدهای نتیجه باشد.

## وبهوک

`_hook_authorized` امضای HMAC-SHA256 بدنه را با secret اپ می‌سازد و با `compare_digest` مقایسه می‌کند. اپی که secret ندارد همهٔ وبهوک‌ها را رد می‌کند (`if not secret: return False`؛ بدون این خط، `compare_digest("", "")` برابر True بود!). حالت `?token=` (برای GitLab) secret را در URL می‌گذارد که ممکن است در لاگ پروکسی‌ها بماند؛ این صادقانه به‌عنوان محدودیت ثبت شده.

## آنچه محافظت نمی‌شود

بخش «Known limitations» در [security.md](../security.md) را با دقت بخوانید: Docker sandbox نیست، build روی daemon میزبان اجرا می‌شود، ساخت دیسک privileged است، اپ‌ها egress آزاد دارند، rate limiting فقط برای ورود است. نوشتن این فهرست نشانهٔ ضعف نیست؛ نشانهٔ این است که تیم می‌داند سیستمش چیست.

## تمرین

1. در `_hook_authorized` خط `if not secret: return False` را حذف کنید و تستی بنویسید که نشان دهد بدون آن چه می‌شود.
2. تابعی بنویسید که بررسی کند `edge_server` با IPv6 خصوصی (`fd00::1`) هم تماس نمی‌گیرد. `ipaddress.ip_address("fd00::1").is_global` چه برمی‌گرداند؟
3. یک endpoint فرضی «دانلود favicon اپ از URL» طراحی کنید. چه کنترل‌هایی لازم است؟ redirect را چطور مدیریت می‌کنید؟ (راهنما: DNS rebinding.)
4. چرا توکن پنل در `localStorage` است و نه کوکی HttpOnly؟ مزایا و معایب هر کدام را بنویسید و نقش CSP را توضیح دهید.
