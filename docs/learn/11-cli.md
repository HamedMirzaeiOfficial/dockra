# فصل ۱۱ — CLI بدون وابستگی

[English](en/11-cli.md) · **فارسی**

## هدف این فصل

ببینید چرا `dockra` یک فایل پایتون با **فقط کتابخانهٔ استاندارد** است، چه هزینه‌ای دارد، و جزئیات امنیتی و شبکه‌ای که یک CLI خوب باید درست انجام دهد.

## چرا بدون وابستگی؟

هدف این بود که CLI روی هر ماشینی که Python دارد نصب شود، **حتی بدون دسترسی به PyPI یا GitHub** (شبکه‌های محدود، فصل‌های قبل). پس:

- `curl -fsSL https://api.example.com/cli/install.sh | sh` فایل `dockra.py` را **از خود سرور** می‌گیرد (`accounts/cli_dist.py`).
- سرور هدر `X-Dockra-Sha256` می‌فرستد و `dockra upgrade` فایل دانلودشده را با آن چک می‌کند.
- برای ویندوز بدون Python، workflow `cli-release.yml` با PyInstaller فایل اجرایی تکی می‌سازد.

هزینه: HTTP با `http.client`، WebSocket کامل (RFC 6455) دست‌نویس در حدود صد خط (`class WebSocket` در `cli/dockra.py`)، پارس argparse بلند. در عوض: صفر مشکل نصب.

## ورود مرورگری و فیشینگ

`dockra login`:

1. CLI `POST /api/auth/cli/start` → یک کد تصادفی.
2. مرورگر صفحهٔ `/cli?code=...` را باز می‌کند؛ کاربر (اگر لازم است) وارد می‌شود و «Connect» می‌زند.
3. CLI هر چند ثانیه `poll` می‌کند و وقتی تأیید شد، یک توکن API می‌گیرد.

حمله: مهاجم خودش `dockra login` می‌زند، **لینک تأیید را برای قربانی می‌فرستد** («لطفاً این را تأیید کن»). قربانی که در پنل وارد است تأیید می‌کند و مهاجم توکن کامل حساب قربانی را می‌گیرد. این حمله در OAuth device flow معروف است. دفاع Dockra (`accounts/cli_web.py`):

- صفحهٔ تأیید **شش نویسهٔ آخر کد** را نشان می‌دهد که CLI در ترمینال چاپ کرده؛ کاربر باید ببیند یکی است.
- متن هشدار صریح: «اگر کسی این لینک را برایتان فرستاده، تأیید نکنید».
- کد ۱۰ دقیقه اعتبار دارد و فقط یک بار تأیید می‌شود.
- فرم‌ها CSRF token دارند و صفحه با CSP سخت (`default-src 'none'`) سرو می‌شود.

## فایل توکن

CLI توکن را در `~/.dockra.json` نگه می‌دارد. نسخهٔ اولیه آن را با `write_text` می‌نوشت؛ یعنی با umask پیش‌فرض، معمولاً `644`: **هر کاربر دیگر روی همان ماشین می‌توانست توکن را بخواند**. روی سرورهای مشترک توسعه این واقعی است. حالا (`_save_login`):

```python
fd = os.open(CONFIG, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o600)
```

فایل از **لحظهٔ ساخت** فقط برای صاحبش خواندنی است (نوشتن و بعد `chmod` یک پنجرهٔ زمانی کوچک باز می‌گذاشت). برای CI هم `DOCKRA_TOKEN` و `DOCKRA_API` از env خوانده می‌شوند تا توکن روی دیسک نوشته نشود. تست `CliCredentialFileTests` هر دو را چک می‌کند.

## آپلود قابل ادامه

`_upload_pieces` فایل‌های بزرگ (بکاپ دیتابیس، آرشیو دیسک) را تکه‌تکه به `/api/uploads` می‌فرستد. سؤال سخت: اگر تکه‌ای رسید ولی **پاسخش گم شد**، کلاینت فکر می‌کند نرسیده و دوباره می‌فرستد. سرور (`engine/uploads.py`) `offset` هر تکه را با اندازهٔ فعلی فایل مقایسه می‌کند؛ اگر نخواند، `409` با `size` فعلی برمی‌گرداند و کلاینت از همان‌جا ادامه می‌دهد. بدون این، تکه‌ای دو بار به فایل اضافه می‌شد و بکاپ خراب می‌شد. این همان ایدهٔ idempotency فصل ۲ در پروتکل شبکه است. قطعی‌ها با backoff (چند ثانیه صبر) دوباره امتحان می‌شوند.

## جزئیات کوچکی که فرق ایجاد می‌کنند

- **فشرده‌سازی هوشمند**: SQL و آرشیو بازنشده قبل از آپلود gzip می‌شوند (چند برابر کوچک‌تر)، ولی فایل‌های media (jpg، mp4) که از قبل فشرده‌اند با سطح ۱ تا زمان هدر نرود.
- **رمز FTP**: با `getpass` پرسیده می‌شود، نه آرگومان خط فرمان، تا در تاریخچهٔ shell نماند.
- **sslip.io روی شبکه‌های محدود**: اگر نام sslip resolve نشود، CLI مستقیم به IP وصل می‌شود و هدر `Host` را درست می‌فرستد.
- **خروجی کاربرپسند**: پیام‌ها می‌گویند قدم بعد چیست («Next: dockra deploy»، «run dockra login again»).

## تمرین

1. `dockra login` را اجرا کنید و کد چاپ‌شده را با کد صفحهٔ مرورگر مقایسه کنید. حالا لینک را در یک مرورگر دیگر با حساب دیگری باز کنید. چه چیزی جلوی اشتباه را می‌گیرد و چه چیزی نمی‌گیرد؟
2. `class WebSocket` را بخوانید. masking frameهای کلاینت چرا لازم است؟ (RFC 6455 بخش 5.3)
3. وسط آپلود یک بکاپ بزرگ اتصال شبکه را قطع کنید (مثلاً با `iptables` یا خاموش کردن Wi-Fi) و دوباره وصل کنید. لاگ CLI چه می‌گوید؟
4. چرا `os.open(..., 0o600)` بهتر از `write_text` و بعد `os.chmod` است؟ سناریوی race را بنویسید.
