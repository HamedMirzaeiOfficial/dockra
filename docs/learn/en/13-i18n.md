# Chapter 13 — Going bilingual: i18n and right-to-left

**English** · [فارسی](../13-i18n.md)

## Goal of this chapter

See how a product becomes bilingual without rewriting its pages: what the translation key should be, where the language comes from, why server-side rendering gets in the way, how the whole layout mirrors in Persian, and how to make sure no text is left untranslated.

## First decision: what is the translation key?

There are two common styles:

| Style | Example | Benefit | Drawback |
| --- | --- | --- | --- |
| Abstract key | `t("apps.empty.title")` | the key stays stable when the text changes | the code becomes meaningless; you must open the translation file to understand a page |
| **English text as the key** | `t("No applications yet")` | readable code; untranslated strings show readable English | when the English text changes, the Persian key must change too |

Dockra chose the second style (`web/lib/i18n.ts`):

```ts
export function t(text: string, vars?: Record<string, string | number>): string {
  const out = current === "fa" ? (FA[text] ?? text) : text;
  if (!vars) return out;
  return out.replace(/\{(\w+)\}/g, (whole, key) => (key in vars ? String(vars[key]) : whole));
}
```

Its drawback is covered by a script (below): if someone changes the English text but not its Persian entry, CI fails.

## Do not build sentences from pieces

A common mistake:

```ts
"Deleted " + name          // ✗
`${count} files transferred` // ✗
```

Word order differs in Persian, and the "pieces" cannot be translated on their own. The right way:

```ts
t("Delete disk {name}?", { name })
t("{files} files transferred.", { files: fmt(count) })
```

The translator sees the whole sentence and decides where `{name}` goes: «دیسک {name} حذف شود؟». Plurals work the same way: instead of `minute${n === 1 ? "" : "s"}` there are two keys (`"{n} minute ago"` and `"{n} minutes ago"`), which are both «{n} دقیقه پیش» in Persian.

## `msg()`: marking without translating

Module-level constant tables (the side menu, range options, plan names) are built **once**, at import time; calling `t()` there would freeze them in the language of that moment. So:

```ts
const MENU = [{ id: "logs", label: msg("Logs") }];  // only a marker: "this text has a translation"
...
<span>{t(item.label)}</span>                         // translated at render time
```

`msg` is the identity function (`return text`), but the checking script uses it to know the string needs a translation.

## Where the language comes from, and why there is no flash

The order of decision: the choice saved in `localStorage`, otherwise the browser's first language (`navigator.languages[0]`), otherwise English. As with the theme (chapter 10), a tiny script **inside `<head>`** (`lib/i18n-script.ts`) sets `lang` and `dir` on `<html>` before any rendering, so the right-to-left layout is correct from the very first frame.

Text has a harder problem, though. Next.js renders pages **on the server**, and the server does not know the user's language. If the server sends English HTML and the browser wants to render Persian, React raises a **hydration mismatch** error (the server HTML does not match the client's first render). There were three options:

1. **The language in the URL** (`/fa/apps`): correct and SEO-friendly, but every route and link changes.
2. **A cookie plus dynamic server rendering:** pages are no longer static.
3. **Render only in the browser:** the panel is an SPA behind a sign-in; its server HTML has no content worth indexing.

Dockra took the third option (`components/lang.tsx`):

```tsx
export function LangGate({ children }) {
  const [ready, setReady] = useState(false);
  const lang = useLang();
  useEffect(() => {
    apply(document.documentElement.lang === "fa" ? "fa" : "en");
    setReady(true);
  }, []);
  return ready ? <Fragment key={lang}>{children}</Fragment> : null;
}
```

Two tricks hide in these few lines:

- **`ready`:** nothing renders until the language is known, so the first render is always in the right language. The cost: a few tens of milliseconds of empty page until JavaScript loads.
- **`key={lang}`:** when the user switches language, the whole tree is remounted under a new key. So plain functions that are not hooks, such as `relTime()`, are called again too, and no component has to "listen" to the language.

## Mirroring the layout

`dir="rtl"` alone is not enough. Physical classes such as `ml-2`, `pl-9`, `left-3` and `text-right` stay in the wrong place in Persian. A script converted all of them to their **logical** equivalents:

| Physical | Logical | Meaning |
| --- | --- | --- |
| `ml-` / `mr-` | `ms-` / `me-` | margin at the start / end of the line |
| `pl-` / `pr-` | `ps-` / `pe-` | padding at the start / end |
| `left-` / `right-` | `start-` / `end-` | position |
| `text-left` | `text-start` | text alignment |
| `border-r` | `border-e` | side border |

A few things are not fixed by logical classes and need `rtl:`: the "back" icon (`rtl:rotate-180`), the Toggle thumb that moves with `translate-x` (`rtl:-translate-x-[18px]`), the select arrow drawn with `background-position`, and the toast progress bar (`rtl:origin-right`).

A real bug turned up right here: in the app creation wizard, the "Back" arrow pointed right **in the English version too**, a leftover from the original Persian version. The fix: the component takes the meaning instead of "left/right":

```tsx
function Chevron({ to }: { to: "back" | "forward" }) { ... className="rtl:-scale-x-100" }
```

## Technical text inside a Persian page

Domain names, file paths, env keys, commands, logs and terminals are left-to-right in every language. Inside a right-to-left paragraph, the Unicode bidirectional algorithm (bidi) moves dots and slashes around (`/app/media` shows up as `app/media/`). So these elements get `dir="ltr"`. Charts are `dir="ltr"` too; the time axis runs left to right in both languages.

For text that comes from the user and whose language we do not know (a deployment message, an alert message), `dir="auto"` lets the browser detect the direction from the first "strong" character.

## Numbers, dates and the percent sign

`lib/format.ts` uses `Intl` with the current language's locale everywhere:

```ts
new Intl.NumberFormat("fa-IR").format(1234.5)        // ۱٬۲۳۴٫۵
new Date().toLocaleString("fa-IR", { dateStyle: "medium" })  // ۲۸ آبان ۱۴۰۵
```

So Persian digits and the Solar Hijri calendar come **for free**, as long as no place hard-codes `"en-US"`. During the conversion, three places with `toLocaleString("en-US")` were found.

The percent sign is a small trap: `"۱۸%"` in a right-to-left paragraph puts `%` on the wrong side. `pct()` uses the Persian percent sign `٪`, which sits correctly next to Persian digits.

## A trap: comparing against translated text

```ts
const color = label === "RAM" ? "bg-info" : "bg-accent";      // ✗ in Persian the label is «رم»
if (phase.startsWith("Uploading")) showProgress();             // ✗
```

Program logic must not depend on display text. In Dockra the second case was fixed with a separate state (`uploading`). The rule: **text is for display only; decisions use identifiers or state.**

## The API side

Error messages (`detail`) and status labels come from Django. The panel sends `Accept-Language` with every request, and Django's `LocaleMiddleware` activates the request's language. `config/i18n.py` uses the same model as the panel:

```python
return Response({"detail": tr("Invalid key: {key}", key=key)}, status=400)
```

Why not Django's standard gettext? gettext needs the GNU tools (`xgettext`, `msgfmt`) on every development machine and in the image, and binary `.mo` files must live in git. A JSON file gives both sides one mental model and is reviewable in a pull request. The cost: no ready-made tools for translators (such as Weblate) out of the box.

To wrap about 200 existing messages, nothing was done by hand. A script using Python's `ast` module found the strings inside `{"detail": ...}` and the first argument of `...Error(...)` calls, and turned f-strings into placeholders:

```python
f"{mount} is already used by disk {owner.name}"
# ↓
tr("{mount} is already used by disk {name}", mount=mount, name=owner.name)
```

A subtle point: worker code has no request, and therefore no active language, so `tr()` returns English. Build logs and Telegram notifications stay in English; this is deliberate, because that text is stored and may later be read by users with different languages.

Model choice labels (`get_status_display()`) are translated in the presentation layer, not in the model, because labels are also stored in migrations and changing them would create pointless migrations.

The server-rendered pages of the CLI (sign-in and approval, deployment tracking) follow the browser's language as well: `_h()` in `accounts/cli_web.py` escapes the translated text first and only then inserts trusted markup (such as `<b>`) into its placeholders, so a translation can never inject HTML.

## Making sure nothing is missing

An incomplete translation fails silently: the page works, one sentence just stays in English. So there are automatic checks:

- `npm run i18n:check` (`web/scripts/i18n-check.mjs`) finds every `t("...")` and `msg("...")` with a regex and fails if a key is missing from `lib/locales/fa/*.json`. With `--report` it also lists JSX text that is not wrapped in `t()` yet.
- `python manage.py i18n_check` does the same for the API with `ast`, plus the labels of every model's choices. It is also called from the tests.
- `engine/test_i18n.py`: the default response is English, it is Persian with `Accept-Language: fa`, and the CLI sign-in page gets `dir="rtl"`.
