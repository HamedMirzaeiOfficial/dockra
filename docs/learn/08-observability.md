# فصل ۸ — پایش و هشدار

[English](en/08-observability.md) · **فارسی**

## هدف این فصل

ببینید عددهایی مثل «۲۹۰ درخواست در دقیقه» و «p95 برابر ۲۲۸ میلی‌ثانیه» از کجا می‌آیند، چرا محاسبه‌شان ظرافت دارد، و هشدار خوب با هشدار پرسروصدا چه فرقی دارد.

## دو منبع داده

| منبع | چه می‌دهد | کجا |
| --- | --- | --- |
| `docker stats` | CPU، رم، شبکهٔ هر کانتینر | `engine/metrics.py` و `DockerDriver.usage_all` |
| metricهای Prometheus خود Traefik | تعداد درخواست، خطای ۵xx، هیستوگرام زمان پاسخ | `engine/traffic.py` |

worker هر دقیقه **یک بار** `docker stats` را برای همهٔ کانتینرها اجرا می‌کند (هر اجرا حدود دو ثانیه است) و نتیجه را در `MetricSample` می‌نویسد. پنل هیچ‌وقت در درخواست کاربر `docker stats` اجرا نمی‌کند؛ از آخرین نمونه می‌خواند. این یعنی صفحهٔ داشبورد با ۵۰ کاربر هم‌زمان هم سرور را سنگین نمی‌کند. قاعدهٔ کلی: **کار گران را از مسیر درخواست بیرون ببرید.**

## شمارندهٔ تجمعی و اختلاف

Traefik می‌گوید `traefik_service_requests_total{service="shop@docker"} 158230`. این عدد از زمان روشن شدن Traefik جمع شده. برای «درخواست در دقیقه» باید اختلاف دو خواندن را گرفت. `_delta` در `traffic.py`:

```python
before = _previous.get(key)
_previous[key] = value
if before is None:
    return 0.0
return value - before if value >= before else value
```

خط آخر مهم است: اگر Traefik ری‌استارت شود، شمارنده از صفر شروع می‌شود و `value < before`. اختلاف منفی معنی ندارد؛ پس فرض می‌کنیم همهٔ مقدار فعلی بعد از ری‌استارت آمده. Prometheus همین منطق را در تابع `rate()` دارد (counter reset).

## چندک از هیستوگرام

میانگین زمان پاسخ گمراه‌کننده است: اگر ۹۵٪ درخواست‌ها ۱۰ms و ۵٪ آن‌ها ۵ ثانیه باشند، میانگین ۲۶۰ms است که هیچ کاربری تجربه‌اش نکرده. p95 می‌گوید «۹۵٪ کاربران سریع‌تر از این عدد جواب گرفتند».

Traefik زمان‌ها را نگه نمی‌دارد؛ فقط می‌گوید چند درخواست زیر ۰.۱ ثانیه، چند تا زیر ۰.۳ و … بودند (سطل‌های تجمعی). `_quantile` جایی را که رتبهٔ ۹۵٪ در آن می‌افتد پیدا می‌کند و **درون سطل خطی درون‌یابی** می‌کند؛ عین `histogram_quantile` در Prometheus. یعنی p95 یک تخمین است و دقتش به مرزهای سطل‌ها بستگی دارد. تست `test_hardening.py` (خط حدود ۳۸۶) با ۱۰۰ درخواست ساختگی این محاسبه را چک می‌کند.

## CPU: یک لحظه یا یک بازه؟

`docker stats --no-stream` یک لحظهٔ حدوداً دوثانیه‌ای است. یک cron دقیقه‌ای که ۲ ثانیه CPU را ۱۰۰٪ می‌کند، اگر لحظهٔ نمونه‌برداری با آن بخورد، نمودار را ۱۰۰٪ نشان می‌دهد. راه‌حل در `drivers.py`: شمارندهٔ تجمعی CPU کانتینر (نانوثانیه) از API داکر خوانده می‌شود و **میانگین از نمونهٔ قبلی تا الان** محاسبه می‌شود. همان ایدهٔ شمارنده و اختلاف، این بار برای CPU.

## هشدار به‌عنوان ماشین حالت

`engine/alerts.py::_set` هشدارها را با دو حالت `firing` و `resolved` نگه می‌دارد:

- اگر شرط برقرار است و هشدار فعالی نیست → ردیف جدید + **یک** اعلان 🚨.
- اگر شرط برقرار است و هشدار فعال هست → فقط پیام به‌روز می‌شود، **بدون** اعلان دوباره.
- اگر شرط برطرف شد و هشدار فعال بود → `resolved` + یک اعلان ✅.

بدون این، هر دقیقه یک پیام «CPU بالاست» به تلگرام می‌رفت و تیم بعد از یک روز کانال را mute می‌کرد. **هشداری که نادیده گرفته شود از نبود هشدار بدتر است.**

چند تصمیم دیگر برای کم کردن نویز:

- CPU و رم باید `DOCKRA_ALERT_MINUTES` دقیقهٔ **پیاپی** بالای آستانه باشند، نه یک لحظه.
- نرخ خطای ۵xx با کمتر از ۲۰ درخواست در بازه هشدار نمی‌دهد (یک خطا از ۲ درخواست یعنی ۵۰٪، ولی معنی‌دار نیست).
- «در دسترس نیست» فقط بعد از سه شکست پشت سر هم.
- اپ متوقف‌شده هشدار فعال نگه نمی‌دارد.

## چه کسی ناظر را نظارت می‌کند؟

اگر worker بمیرد، کی هشدار «worker مرده» را می‌فرستد؟ worker و terminal هر کدام ضربان (`ServiceBeat`) می‌نویسند و **همدیگر** را می‌پایند. `/api/health` هم اگر سرویسی ساکت باشد 503 می‌دهد تا یک ابزار بیرونی (Uptime Kuma و …) بتواند خود پلتفرم را پایش کند. خاموش شدن عادی (SIGTERM) ردیف را پاک می‌کند تا کم کردن تعداد builderها هشدار کاذب ندهد.

## تمرین

1. `_quantile` را با این سطل‌ها روی کاغذ اجرا کنید: `[(0.05, 10), (0.1, 70), (0.3, 100), (inf, 100)]` و `q=0.95`. جواب را با تست مقایسه کنید.
2. اگر Traefik بین دو خواندن **دو بار** ری‌استارت شود و شمارنده از عدد قبلی بزرگ‌تر باشد، `_delta` چه اشتباهی می‌کند؟ آیا قابل تشخیص است؟
3. یک قاعدهٔ هشدار جدید طراحی کنید: «حافظهٔ اپ در یک ساعت گذشته مدام رشد کرده» (نشت حافظه). داده‌اش در `MetricSample` هست؟ چطور نویز را کم می‌کنید؟
4. چرا نمودارها حداکثر ۲۴۰ نقطه دارند؟ با ۷ روز دادهٔ دقیقه‌ای (۱۰٬۰۸۰ نمونه) مرورگر چه مشکلی پیدا می‌کرد؟
