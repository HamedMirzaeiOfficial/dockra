# فصل ۷ — ترمینال و WebSocket

## هدف این فصل

ببینید یک ترمینال تعاملی واقعی (با رنگ، `vim`، `htop`) چطور از مرورگر تا داخل کانتینر می‌رسد، و چرا این سرویس جدا از API اجرا می‌شود.

## چرا سرویس جدا؟

Gunicorn چند پروسه با چند thread دارد (`--workers 3 --threads 8` در `api/Dockerfile`). هر اتصال WebSocket ترمینال ممکن است ساعت‌ها باز بماند. اگر روی Gunicorn بود، ۲۴ ترمینال باز یعنی API کاملاً قفل. سرویس `terminal` (`engine/terminal.py`) روی `asyncio` و کتابخانهٔ `websockets` است: هزاران اتصال باز در یک پروسه، چون هر اتصال فقط وقتی داده دارد CPU مصرف می‌کند.

## بلیت: احراز هویت بدون اشتراک نشست

سرویس terminal نشست Django ندارد. پس چطور بفهمد کاربر کیست؟

1. پنل `POST /api/apps/shop/terminal` می‌زند (با JWT معمولی). API مجوز را بررسی می‌کند.
2. API یک **بلیت امضاشده** می‌سازد (`django.core.signing`) شامل نوع، کاربر و هدف، با اعتبار ۶۰ ثانیه، و آدرس WebSocket را برمی‌گرداند.
3. مرورگر با بلیت به terminal وصل می‌شود. terminal امضا را بررسی می‌کند، **یک بار مصرفش می‌کند** (جلوی replay)، و نقش و سازمان را **دوباره** از دیتابیس می‌خواند (شاید کاربر در این ۶۰ ثانیه غیرفعال شده).

این الگو در هر سیستمی که سرویس‌های جدا دارد تکرار می‌شود: یک سرویس مجوز می‌دهد، یک توکن کوتاه‌عمر و محدود صادر می‌کند، سرویس دیگر فقط همان را می‌پذیرد.

## pty: چرا `docker exec -it` کافی نیست؟

برنامه‌هایی مثل `vim` فقط وقتی درست کار می‌کنند که stdin آن‌ها یک **ترمینال** باشد، نه pipe. سرویس terminal:

1. یک pty (pseudo-terminal) باز می‌کند: یک جفت master/slave.
2. `docker exec -it ... sh` را با slave به‌عنوان stdin/stdout/stderr اجرا می‌کند، با `setsid` (نشست جدید) و `TIOCSCTTY` (این pty ترمینال کنترل‌کنندهٔ نشست است). بدون این‌ها Ctrl+C به پروسهٔ درست نمی‌رسد.
3. بایت‌های master را به WebSocket می‌فرستد (frame باینری) و برعکس.
4. وقتی پنجرهٔ مرورگر عوض می‌شود، پیام `{"type":"resize","cols":..,"rows":..}` با `ioctl(TIOCSWINSZ)` به pty اعمال می‌شود تا `vim` اندازهٔ درست را بداند.

یک نکته از کامنت کد: شل **login** اجرا نمی‌شود، چون `/etc/profile` در Debian و Alpine متغیر `PATH` را بازنویسی می‌کند و `/venv/bin` ایمیج Django گم می‌شود.

در پنل، `xterm.js` (`web/components/terminal.tsx`) همان شبیه‌ساز ترمینال VS Code است و بایت‌های خام را رندر می‌کند.

## بایت، نه متن

خروجی را به‌صورت frame **باینری** می‌فرستیم، نه متن. چرا؟ یک کاراکتر UTF-8 چندبایتی (مثلاً «ش» دو بایت است) ممکن است بین دو `read()` بشکند. اگر هر تکه را جدا decode کنیم، کاراکتر خراب می‌شود. با فرستادن بایت خام، `xterm.js` خودش decoder پیوسته دارد. CLI هم همین کار را می‌کند (کامنت «Raw bytes, so multi-byte UTF-8 characters never split» در `cli/dockra.py`).

## tunnel دیتابیس

`dockra db connect myapp-db` یک پورت روی `127.0.0.1` لپ‌تاپ باز می‌کند. هر اتصال TCP به آن، یک WebSocket با بلیت `tunnel` به سرویس terminal باز می‌کند و سرویس به `host:port` دیتابیس روی شبکهٔ `dockra` وصل می‌شود و بایت‌ها را دو طرفه رد می‌کند. یعنی TCP روی WebSocket روی HTTPS. نتیجه: دیتابیس هیچ پورتی روی اینترنت ندارد، ولی `psql` و DBeaver روی لپ‌تاپ مستقیم کار می‌کنند.

## لاگ زنده و تشخیص قطع اتصال

لاگ زنده `docker logs -f` همهٔ نمونه‌ها را در یک thread می‌خواند. مشکل: اگر کاربر تب را ببندد و هیچ لاگی نیاید، سرور تا ابد نمی‌فهمد و پروسه‌های `docker logs` می‌مانند. راه‌حل: هر ۱۵ ثانیه یک خط خالی فرستاده می‌شود؛ اگر فرستادن شکست بخورد، اتصال مرده و پروسه‌ها کشته می‌شوند. این همان ایدهٔ heartbeat فصل ۲ است، این بار برای اتصال شبکه.

## تمرین

1. با `dockra shell` وارد کانتینر شوید، `vim` را باز کنید و پنجرهٔ ترمینال را کوچک و بزرگ کنید. حالا با `dockra shell --line` همین را امتحان کنید. فرق چیست و چرا؟
2. در `engine/terminal.py` تابعی را پیدا کنید که بلیت را «یک بار مصرف» می‌کند. اگر دو مرورگر هم‌زمان با یک بلیت وصل شوند چه می‌شود؟
3. یک اتصال `psql` را از طریق `dockra db connect` باز کنید و در سرور با `ss -tnp` ببینید کدام پروسه به پورت ۵۴۳۲ دیتابیس وصل است.
4. چرا بلیت ۶۰ ثانیه و نه ۱۰ دقیقه؟ چه چیزی را کوتاه‌تر کردن آن خراب می‌کند؟
