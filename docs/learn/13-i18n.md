# فصل ۱۳ — دو زبانه کردن: i18n و راست‌به‌چپ

[English](en/13-i18n.md) · **فارسی**

## هدف این فصل

ببینید یک محصول چطور بدون بازنویسی صفحه‌ها دو زبانه می‌شود: کلید ترجمه چه باشد، زبان از کجا تعیین شود، چرا رندر سمت سرور مشکل‌ساز است، چطور کل چیدمان در فارسی آینه می‌شود و چطور مطمئن شویم هیچ متنی بی‌ترجمه نمی‌ماند.

## تصمیم اول: کلید ترجمه چیست؟

دو سبک رایج داریم:

| سبک | مثال | مزیت | عیب |
| --- | --- | --- | --- |
| کلید انتزاعی | `t("apps.empty.title")` | کلید ثابت می‌ماند اگر متن عوض شود | کد را بی‌معنی می‌کند؛ برای فهمیدن صفحه باید فایل ترجمه را باز کرد |
| **متن انگلیسی به‌عنوان کلید** | `t("No applications yet")` | کد خواناست؛ ترجمه‌نشده‌ها انگلیسی خوانا نشان داده می‌شوند | با تغییر متن انگلیسی، کلید فارسی هم باید عوض شود |

Dockra سبک دوم را انتخاب کرده (`web/lib/i18n.ts`):

```ts
export function t(text: string, vars?: Record<string, string | number>): string {
  const out = current === "fa" ? (FA[text] ?? text) : text;
  if (!vars) return out;
  return out.replace(/\{(\w+)\}/g, (whole, key) => (key in vars ? String(vars[key]) : whole));
}
```

عیبش را با یک اسکریپت جبران می‌کنیم (پایین‌تر): اگر کسی متن انگلیسی را عوض کند و فارسی‌اش را نه، CI می‌شکند.

## جمله را تکه‌تکه نسازید

اشتباه رایج:

```ts
"Deleted " + name          // ✗
`${count} files transferred` // ✗
```

ترتیب کلمات در فارسی فرق می‌کند و «تکه»ها جدا جدا قابل ترجمه نیستند. درست:

```ts
t("Delete disk {name}?", { name })
t("{files} files transferred.", { files: fmt(count) })
```

مترجم کل جمله را می‌بیند و جای `{name}` را خودش انتخاب می‌کند: «دیسک {name} حذف شود؟». جمع و مفرد هم همین‌طور: به‌جای `minute${n === 1 ? "" : "s"}` دو کلید جدا داریم (`"{n} minute ago"` و `"{n} minutes ago"`) که در فارسی هر دو «{n} دقیقه پیش» هستند.

## `msg()`: علامت‌گذاری بدون ترجمه

جدول‌های ثابت سطح ماژول (منوی کناری، گزینه‌های بازه، نام پلن‌ها) **یک بار** هنگام import ساخته می‌شوند؛ اگر آن‌جا `t()` صدا بزنیم، با زبان لحظهٔ import ثابت می‌مانند. پس:

```ts
const MENU = [{ id: "logs", label: msg("Logs") }];  // فقط علامت: «این متن ترجمه دارد»
...
<span>{t(item.label)}</span>                         // ترجمه در لحظهٔ رندر
```

`msg` تابع همانی است (`return text`)، ولی اسکریپت بررسی از روی آن می‌فهمد این رشته باید ترجمه داشته باشد.

## زبان از کجا می‌آید و چرا «فلش» نداریم

ترتیب تصمیم: انتخاب ذخیره‌شده در `localStorage`، وگرنه زبان اول مرورگر (`navigator.languages[0]`)، وگرنه انگلیسی. مثل تم (فصل ۱۰)، یک اسکریپت کوچک **داخل `<head>`** (`lib/i18n-script.ts`) قبل از هر رندری `lang` و `dir` را روی `<html>` می‌گذارد تا چیدمان راست‌به‌چپ از اولین فریم درست باشد.

ولی متن‌ها مسئلهٔ سخت‌تری دارند. Next.js صفحه‌ها را **روی سرور** رندر می‌کند و سرور زبان کاربر را نمی‌داند. اگر سرور HTML انگلیسی بدهد و مرورگر بخواهد فارسی رندر کند، React خطای **hydration mismatch** می‌دهد (HTML سرور با رندر اول کلاینت نمی‌خواند). سه راه داشتیم:

1. **زبان در URL** (`/fa/apps`): درست و SEO‌پسند، ولی همهٔ مسیرها و لینک‌ها عوض می‌شوند.
2. **کوکی + رندر پویا روی سرور:** صفحه‌ها دیگر static نیستند.
3. **رندر فقط در مرورگر:** پنل یک SPA پشت ورود است؛ HTML سرور محتوای ارزشمندی برای ایندکس ندارد.

Dockra راه سوم را برداشته (`components/lang.tsx`):

```tsx
export function LangGate({ children }) {
  const [ready, setReady] = useState(false);
  const lang = useLang();
  useEffect(() => {
    apply(document.documentElement.lang === "fa" ? "fa" : "en");
    setReady(true);
  }, []);
  return ready ? <Fragment key={lang}>{children}</Fragment> : null;
}
```

دو ترفند در این چند خط هست:

- **`ready`:** تا زبان معلوم نشده چیزی رندر نمی‌شود؛ پس رندر اول همیشه با زبان درست است. هزینه: چند ده میلی‌ثانیه صفحهٔ خالی تا JavaScript بار شود.
- **`key={lang}`:** وقتی کاربر زبان را عوض می‌کند، کل درخت با کلید جدید از نو mount می‌شود. پس توابع ساده‌ای مثل `relTime()` که hook نیستند هم دوباره صدا زده می‌شوند و لازم نیست هر کامپوننت به زبان «گوش بدهد».

## آینه کردن چیدمان

فقط `dir="rtl"` کافی نیست. کلاس‌های فیزیکی مثل `ml-2`، `pl-9`، `left-3` و `text-right` در فارسی جای اشتباه می‌مانند. همهٔ آن‌ها با یک اسکریپت به معادل **منطقی** تبدیل شدند:

| فیزیکی | منطقی | معنی |
| --- | --- | --- |
| `ml-` / `mr-` | `ms-` / `me-` | فاصله از ابتدا / انتهای خط |
| `pl-` / `pr-` | `ps-` / `pe-` | padding ابتدا / انتها |
| `left-` / `right-` | `start-` / `end-` | موقعیت |
| `text-left` | `text-start` | چینش متن |
| `border-r` | `border-e` | خط کنار |

چند چیز با کلاس منطقی درست نمی‌شود و `rtl:` لازم دارد: آیکون «بازگشت» (`rtl:rotate-180`)، دایرهٔ کلید Toggle که با `translate-x` حرکت می‌کند (`rtl:-translate-x-[18px]`)، فلش select که با `background-position` کشیده شده، و نوار پیشرفت toast (`rtl:origin-right`).

یک باگ واقعی همین‌جا پیدا شد: در wizard ساخت برنامه، فلش «بازگشت» **در نسخهٔ انگلیسی هم** به راست اشاره می‌کرد؛ یادگار نسخهٔ فارسی اولیه بود. راه‌حل: کامپوننت به‌جای «چپ/راست» معنی را بگیرد:

```tsx
function Chevron({ to }: { to: "back" | "forward" }) { ... className="rtl:-scale-x-100" }
```

## متن فنی داخل صفحهٔ فارسی

نام دامنه، مسیر فایل، کلید متغیر محیطی، فرمان، لاگ و ترمینال در هر زبانی چپ‌به‌راست‌اند. اگر داخل پاراگراف راست‌به‌چپ بیایند، الگوریتم دوجهتهٔ یونیکد (bidi) نقطه و اسلش را جابه‌جا نشان می‌دهد (`/app/media` می‌شود `app/media/`). پس این عناصر `dir="ltr"` می‌گیرند. نمودارها هم `dir="ltr"` دارند؛ محور زمان در هر دو زبان از چپ به راست است.

برای متنی که از کاربر می‌آید و نمی‌دانیم چه زبانی است (پیام استقرار، پیام هشدار) `dir="auto"` می‌گذاریم تا مرورگر از اولین حرف «قوی» جهت را تشخیص دهد.

## عدد، تاریخ و درصد

`lib/format.ts` همه‌جا از `Intl` با locale زبان فعلی استفاده می‌کند:

```ts
new Intl.NumberFormat("fa-IR").format(1234.5)        // ۱٬۲۳۴٫۵
new Date().toLocaleString("fa-IR", { dateStyle: "medium" })  // ۲۸ آبان ۱۴۰۵
```

یعنی ارقام فارسی و تقویم شمسی **رایگان** است، به شرط اینکه هیچ‌جا `"en-US"` دستی نوشته نشده باشد. هنگام تبدیل، سه جا پیدا شد که `toLocaleString("en-US")` داشتند.

علامت درصد هم یک دام کوچک است: «۱۸%» در پاراگراف راست‌به‌چپ `%` را سمت اشتباه می‌گذارد. `pct()` از علامت درصد فارسی `٪` استفاده می‌کند که کنار ارقام فارسی درست می‌نشیند.

## یک دام: مقایسه با متن ترجمه‌شده

```ts
const color = label === "RAM" ? "bg-info" : "bg-accent";      // ✗ در فارسی label «رم» است
if (phase.startsWith("Uploading")) showProgress();             // ✗
```

منطق برنامه نباید به متن نمایشی وابسته باشد. در Dockra دومی با یک state جدا (`uploading`) درست شد. قاعده: **متن فقط برای نمایش است؛ برای تصمیم از شناسه یا state استفاده کنید.**

## سمت API

پیام‌های خطا (`detail`) و برچسب‌های وضعیت از Django می‌آیند. پنل در هر درخواست `Accept-Language` می‌فرستد و `LocaleMiddleware` جنگو زبان درخواست را فعال می‌کند. `config/i18n.py` همان مدل پنل را دارد:

```python
return Response({"detail": tr("Invalid key: {key}", key=key)}, status=400)
```

چرا gettext استاندارد جنگو نه؟ gettext ابزارهای GNU (`xgettext`، `msgfmt`) را روی هر ماشین توسعه و در image لازم دارد و فایل‌های باینری `.mo` باید در git باشند. یک فایل JSON برای هر دو طرف یک مدل ذهنی می‌سازد و در pull request قابل بازبینی است. هزینه‌اش: ابزارهای آماده برای مترجم‌ها (مثل Weblate) را مستقیم نداریم.

برای وصل کردن حدود ۲۰۰ پیام موجود، دستی کار نکردیم. یک اسکریپت با ماژول `ast` پایتون رشته‌های داخل `{"detail": ...}` و آرگومان اول `...Error(...)` را پیدا کرد و f-stringها را به placeholder تبدیل کرد:

```python
f"{mount} is already used by disk {owner.name}"
# ↓
tr("{mount} is already used by disk {name}", mount=mount, name=owner.name)
```

نکتهٔ ظریف: کد worker درخواستی ندارد، پس زبان فعالی هم ندارد و `tr()` انگلیسی برمی‌گرداند. لاگ ساخت و اعلان تلگرام انگلیسی می‌مانند؛ این آگاهانه است، چون آن متن‌ها ذخیره می‌شوند و بعداً ممکن است کاربرانی با زبان‌های مختلف ببینندشان.

برچسب choices مدل‌ها (`get_status_display()`) در لایهٔ present ترجمه می‌شوند، نه در خود مدل؛ چون برچسب‌ها در migrationها هم ذخیره می‌شوند و تغییرشان migration بی‌دلیل می‌سازد.

صفحه‌های سمت سرورِ CLI (ورود و تأیید، پیگیری استقرار) هم از زبان مرورگر پیروی می‌کنند: `_h()` در `accounts/cli_web.py` اول متن ترجمه‌شده را escape می‌کند و بعد markup مطمئن (مثل `<b>`) را در placeholderها می‌گذارد؛ پس ترجمه هیچ‌وقت نمی‌تواند HTML تزریق کند.

## مطمئن شدن از کامل بودن

ترجمهٔ ناقص بی‌صدا خراب می‌شود: صفحه کار می‌کند، فقط یک جمله انگلیسی می‌ماند. پس بررسی خودکار داریم:

- `npm run i18n:check` (`web/scripts/i18n-check.mjs`): همهٔ `t("...")` و `msg("...")` را با regex پیدا می‌کند و اگر کلیدی در `lib/locales/fa/*.json` نباشد خطا می‌دهد. با `--report` متن‌های JSX را که هنوز داخل `t()` نیستند هم فهرست می‌کند.
- `python manage.py i18n_check`: همین کار برای API با `ast` به‌علاوهٔ برچسب همهٔ choices مدل‌ها. خودش داخل تست‌ها هم صدا زده می‌شود.
- `engine/test_i18n.py`: پاسخ پیش‌فرض انگلیسی است، با `Accept-Language: fa` فارسی است، و صفحهٔ ورود CLI `dir="rtl"` می‌گیرد.

## تمرین

1. یک متن جدید به پنل اضافه کنید (مثلاً زیرعنوان صفحهٔ Domains) و `npm run i18n:check` را اجرا کنید. پیام خطا چه می‌گوید؟ ترجمه را اضافه کنید.
2. در `lib/i18n.ts` وقتی کلید فارسی نیست، به‌جای انگلیسی `"⚠ " + text` برگردانید و پنل را در فارسی ببینید. این روش برای پیدا کردن جاهای جاافتاده چه مزیتی بر اسکریپت دارد و چه عیبی؟
3. `<LangGate>` را بردارید و `t()` را مستقیم استفاده کنید. کنسول مرورگر چه خطایی می‌دهد؟ چرا؟
4. یک زبان سوم (مثلاً عربی) اضافه کنید. کدام فایل‌ها تغییر می‌کنند؟ آیا چیدمان راست‌به‌چپ کار اضافه‌ای لازم دارد؟
5. در API پیام `"Range must be 1h, 6h, 24h or 7d"` را با `curl -H 'Accept-Language: fa'` ببینید. چرا خود `1h` و `7d` ترجمه نشده‌اند؟
