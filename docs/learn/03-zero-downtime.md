# فصل ۳ — استقرار بدون قطعی

[English](en/03-zero-downtime.md) · **فارسی**

## هدف این فصل

ببینید یک نسخهٔ جدید چطور بالا می‌آید بدون اینکه حتی یک درخواست کاربر خطا بگیرد، و اگر نسخهٔ جدید خراب بود چرا نسخهٔ قبلی دست نمی‌خورد.

## روش ساده و غلط

```
docker stop app && docker rm app && docker run new-image
```

بین `stop` و آماده شدن نسخهٔ جدید (که ممکن است ۲۰ ثانیه طول بکشد) سایت پایین است. بدتر: اگر نسخهٔ جدید اصلاً بالا نیاید، سایت پایین می‌ماند.

## روش Dockra: کنار هم، بعد جایگزین

`DockerDriver.build_and_run` و `_launch` در `api/engine/drivers.py`:

1. **build** با BuildKit. اگر شکست بخورد، هیچ کانتینری عوض نشده.
2. **release**: دستوری مثل `python manage.py migrate` یک بار در یک کانتینر یک‌بارمصرف با همان env و دیسک‌ها. اگر شکست بخورد: «نسخهٔ فعلی دست نخورد».
3. **launch**: نمونه‌های جدید با نام `dockra-app-<slug>-<release>-<n>` و **همان برچسب سرویس Traefik** بالا می‌آیند. Traefik بلافاصله ترافیک را بین قدیمی و جدید پخش می‌کند.
4. **health check**: `_wait_ready` وضعیت کانتینر، `HEALTHCHECK` ایمیج و یک probe مستقیم (TCP یا HTTP روی `healthCheck.path`) را تا `DOCKRA_HEALTH_TIMEOUT` بررسی می‌کند.
5. **موفق**: نمونه‌های قدیمی با `docker stop -t 10` (فرصت تمام کردن درخواست‌های در جریان)، بایگانی لاگ و `rm` حذف می‌شوند.
6. **ناموفق**: نمونه‌های **جدید** حذف می‌شوند و خطا با لاگشان بالا می‌رود.

این الگو یک نوع **rolling / blue-green** ساده روی یک ماشین است. کل مرحلهٔ ۳ تا ۶ زیر `app_lock` است (فصل ۲).

## یک ظرافت: Traefik باید بتواند برسد

هر اپ شبکهٔ خودش را دارد (فصل ۵). `_ensure_app_network` قبل از هر بالا آمدن مطمئن می‌شود Traefik به آن شبکه وصل است. اگر Traefik دوباره ساخته شود (مثلاً با به‌روزرسانی compose)، به شبکهٔ اپ‌ها وصل نیست و همهٔ سایت‌ها timeout می‌شوند! برای همین `reconnect_routes` هر ۳۰ ثانیه شبکه‌های جاافتاده را دوباره وصل می‌کند. این باگ واقعی در تاریخچهٔ پروژه بوده (فصل ۱۲).

## migration و سازگاری رو به عقب

در مرحلهٔ ۳، برای چند ثانیه **هر دو نسخه** هم‌زمان ترافیک می‌گیرند و هر دو به یک دیتابیس وصل‌اند که migration جدید رویش اجرا شده. پس migration باید طوری باشد که **کد قدیمی هم با اسکیمای جدید کار کند**. مثلاً حذف یک ستون را در دو استقرار انجام دهید: اول کد را طوری عوض کنید که از ستون استفاده نکند، در استقرار بعد ستون را حذف کنید. این قاعده برای خود Dockra هم صادق است (`docs/development.md`).

## rollback

`_rollback` در `engine/runner.py` image ذخیره‌شدهٔ همان نسخه را با **همان مسیر بدون قطعی** بالا می‌آورد، ولی با `release=""`؛ یعنی migrationها دوباره اجرا یا برگردانده نمی‌شوند. rollback کد را برمی‌گرداند، نه داده را. به همین دلیل migration سازگار مهم است.

## لغو

لغو دو حالت دارد (`request_cancel` در runner):

- **در صف**: Job و Deployment همان لحظه پایان می‌گیرند. ساده.
- **در حال ساخت**: پروسهٔ `docker build` در worker دیگری است. API فقط `cancel_requested=True` می‌گذارد. در `_stream` (drivers.py) یک نخ ناظر هر چند ثانیه این پرچم را از دیتابیس می‌خواند و اگر روشن بود پروسه را می‌کشد و `BuildCanceled` پرتاب می‌کند. ارتباط بین پروسه‌ها **از طریق دیتابیس** است، نه سیگنال.

## تغییر تنظیمات هم بدون قطعی است

تغییر env، دامنه، دیسک یا منابع یک `Job(sync)` می‌سازد که از همان `_launch` رد می‌شود. اگر اعمال روی کانتینر شکست بخورد، API صادقانه می‌گوید «ذخیره شد ولی اعمال نشد» (502)، نه «موفق».

## تمرین

1. `_wait_ready` را بخوانید. اگر اپ روی پورت گوش بدهد ولی `/health/` آن ۵۰۰ برگرداند چه می‌شود؟ اگر ۴۰۴ برگرداند چه؟ چرا این تصمیم گرفته شده؟
2. تست `test_failed_build_keeps_the_previous_release_live` را بخوانید و یک تست مشابه برای شکست **release command** بنویسید.
3. چرا `docker stop -t 10` و نه `docker kill`؟ اپ Django زیر Gunicorn با SIGTERM چه می‌کند؟
4. یک migration طراحی کنید که نام یک ستون را عوض کند و در هیچ لحظه‌ای از استقرار بدون قطعی خطا ندهد.
