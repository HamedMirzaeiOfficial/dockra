# امنیت

[English](../security.md) · **فارسی**

Dockra برای تیمی طراحی شده که برنامه‌های **خودش** را روی سرور **خودش** اجرا می‌کند. این صفحه می‌گوید پلتفرم از چه چیزی و چطور محافظت می‌کند و، به همان اندازه مهم، از چه چیزی محافظت نمی‌کند.

## مدل تهدید

| در محدوده | خارج از محدوده |
| --- | --- |
| فردی بیرونی در اینترنت که می‌خواهد به API، داشبورد، دیتابیس‌ها یا برنامه‌های دیگر برسد | مستأجرهای مهاجمی که عمداً کد مخرب اجرا می‌کنند ([محدودیت‌ها](#محدودیت‌های-شناخته‌شده) را ببینید) |
| عضو تیمی که فراتر از نقشش عمل می‌کند (بیننده‌ای که مستقر می‌کند، توسعه‌دهنده‌ای که حذف می‌کند) | سیستم‌عامل یا Docker نفوذشدهٔ سرور |
| عضو یک سازمان که به منابع سازمان دیگری می‌رسد | دسترسی فیزیکی به سرور یا دیسک‌هایش |
| باگی در یک برنامه که برنامهٔ دیگر یا دیتابیس خود پلتفرم را لو بدهد | حملهٔ زنجیرهٔ تأمین روی ایمیج‌های پایه و بسته‌هایی که برنامه‌هایتان نصب می‌کنند |
| سرقت نشست، فیشینگ ورود CLI، حدس رمز | حملهٔ منع سرویس در سطح شبکه |

اجرای این قواعد در `accounts.permissions.IsMember` متمرکز است: خواندن عضویت لازم دارد و نوشتن `write_role` همان view را (پیش‌فرض توسعه‌دهنده). هر جست‌وجوی شیء به `request.membership.organization` محدود است؛ پس منابع سازمان‌های دیگر 404 برمی‌گردانند، نه 403. تست‌ها: `engine/test_platform.py`، `engine/tests.py`، `engine/test_hardening.py`.

همه (حتی بیننده‌ها) رمز، 2FA و توکن‌های API خودشان را مدیریت می‌کنند؛ هر توکن نقش صاحبش را دارد. نقش مالک متعلق به `admin` اولیه است و از طریق API تغییر نمی‌کند؛ فقط مالک مدیران را مدیریت می‌کند و هیچ‌کس نقش خودش را تغییر نمی‌دهد.

## احراز هویت

- **داشبورد:** JWT (۱۲ ساعت) همراه با نسخهٔ نشست (`sv`). خروج، تغییر رمز، بازنشانی رمز توسط مدیر و غیرفعال شدن، نسخه را یکی بالا می‌برند و همهٔ توکن‌های صادرشده را بلافاصله باطل می‌کنند.
- **ورود مرورگری CLI:** کدی یک‌بارمصرف که ۱۰ دقیقه اعتبار دارد و فقط یک بار تأیید می‌شود. صفحهٔ تأیید شش نویسهٔ آخر کدی را که `dockra login` چاپ کرده نشان می‌دهد و هشدار می‌دهد که تأیید لینک شخص دیگر به او دسترسی کامل می‌دهد (فیشینگ). فرم‌ها توکن CSRF دارند و صفحه‌ها با CSP سخت‌گیرانه (`default-src 'none'`) سرو می‌شوند. تأیید یک توکن API با اعتبار `DOCKRA_CLI_TOKEN_DAYS` (پیش‌فرض ۳۶۵ روز) صادر می‌کند.
- **توکن‌های API:** با پیشوند `dockra_`، فقط یک بار نمایش داده می‌شوند، فقط هش sha256 آن‌ها ذخیره می‌شود، انقضای اختیاری دارند و قابل ابطال‌اند.
- **رمزها:** اعتبارسنج‌های Django (حداقل طول، رمزهای رایج، فقط عدد).
- **محدودیت تلاش:** ۸ تلاش ناموفق در ۱۵ دقیقه برای هر IP *یا* هر نام کاربری، ورود را موقتاً مسدود می‌کند (داشبورد و CLI). `X-Forwarded-For` فقط وقتی پذیرفته می‌شود که درخواست از یک proxy مورد اعتماد بیاید (`DOCKRA_TRUSTED_PROXIES`، پیش‌فرض Traefik) که هر مقدار ارسالی کلاینت را بازنویسی می‌کند.
- **2FA با TOTP:** هر برنامهٔ احراز هویتی؛ ۸ کد بازیابی یک‌بارمصرف که به‌صورت هش ذخیره می‌شوند؛ هر کد ۶ رقمی فقط یک بار پذیرفته می‌شود (محافظت در برابر تکرار)؛ ‎±۳۰ ثانیه اختلاف ساعت مجاز است.

## رازها

با Fernet و کلیدی که از `DOCKRA_ENCRYPTION_KEY` مشتق می‌شود (در نبودش `DJANGO_SECRET_KEY`) رمزنگاری‌شده ذخیره می‌شوند:

- مقدار همهٔ متغیرهای محیطی برنامه‌ها،
- رمز دیتابیس‌ها،
- رمز وب‌هوک‌ها،
- کلیدهای TOTP کاربران.

قواعد کار با آن‌ها:

- متغیرها با `--env-file` به کانتینر می‌رسند، هیچ‌وقت به‌صورت آرگومان خط فرمان که در فهرست پروسه‌های سرور دیده شود.
- مقادیری که محرمانه علامت خورده‌اند برای بیننده‌ها پوشانده می‌شوند (`••••••`)؛ اگر کلاینت همین ماسک را برگرداند، API راز ذخیره‌شده را با آن بازنویسی نمی‌کند.
- رمزهای FTP که برای درون‌ریزی دیسک استفاده می‌شوند در جدول کارها ذخیره نمی‌شوند.
- CLI رمز FTP را به‌صورت تعاملی می‌پرسد تا در تاریخچهٔ shell نماند.

**چیزهایی که Dockra رمزنگاری نمی‌کند:** داده‌های برنامه و دیتابیس روی دیسک‌ها، فایل‌های بکاپ روی سرور و نسخه‌های S3 خارج از سرور. bucket را خصوصی نگه دارید و دسترسی به `/var/lib/dockra` را محدود کنید.

## ایزوله‌سازی

- **سوکت Docker.** سرویس `api`، تنها سرویسی که مستقیم درخواست‌های کاربر را پارس می‌کند، به `docker.sock` دسترسی ندارد. worker، builder و terminal دارند که معادل root روی سرور است؛ آن‌ها فقط روی کارهایی عمل می‌کنند که API بعد از بررسی مجوز در صف گذاشته است.
- **کانتینرها.** هر برنامه با سقف CPU (`--cpus`، `--cpu-shares`)، حافظه (بدون swap) و PID و گزینهٔ `--security-opt no-new-privileges` اجرا می‌شود. قالب‌های داخلی با کاربر غیر root (uid 1000) اجرا می‌شوند. اولویت OOM طوری است که کرنل اول برنامه‌ها، بعد دیتابیس‌ها و در آخر سرویس‌های پلتفرم را می‌کشد.
- **شبکه‌ها.** هر برنامه شبکهٔ خودش را دارد. فقط نمونه‌هایش، Traefik، worker یا builderی که سلامتش را بررسی می‌کند و دیتابیس‌هایی که صراحتاً به آن وصل شده‌اند عضو این شبکه‌اند. برنامه‌ها به برنامه‌های دیگر، دیتابیس‌های وصل‌نشده، دیتابیس پلتفرم یا سرویس‌های پلتفرم دسترسی ندارند. رابط‌های مدیریت دیتابیس شبکهٔ جدایی فقط با Traefik و یک دیتابیس دارند.
- **دیتابیس‌ها** هیچ پورتی روی سرور منتشر نمی‌کنند؛ دسترسی بیرونی فقط از تونل احراز هویت‌شده با بلیت ممکن است (`dockra db connect`).
- **ترمینال و تونل‌ها** از بلیت‌های امضاشدهٔ یک‌بارمصرف با اعتبار ۶۰ ثانیه استفاده می‌کنند؛ نقش و سازمان هنگام اتصال دوباره بررسی می‌شوند و هر نشست در گزارش فعالیت ثبت می‌شود.

## گزارش فعالیت

در تنظیمات و در `GET /api/audit` دیده می‌شود: استقرارها (دستی و خودکار)، بازگشت‌ها، چرخهٔ عمر دیتابیس، بکاپ و بازگردانی، فرمان‌های کنسول (با متن فرمان)، نشست‌های ترمینال، تونل‌های دیتابیس، تغییرات وب‌هوک، آپلود و حذف فایل‌های دیسک، چرخهٔ عمر برنامه و هر تغییر عضویت.

## محدودیت‌های شناخته‌شده

- **Docker محیط امنی برای کد مهاجم نیست.** کانتینرها کرنل سرور را به اشتراک می‌گذارند. یک آسیب‌پذیری در کرنل یا محیط اجرا می‌تواند به نفوذ به سرور برسد. از Dockra برای اجرای کد کاربران غیرقابل‌اعتماد استفاده نکنید. ایزوله‌سازی قوی‌تر (gVisor، Kata Containers، ماشین مجازی جدا برای هر مستأجر) در نقشهٔ راه است.
- **ساخت‌ها روی Docker خود سرور اجرا می‌شوند.** یک `Dockerfile` می‌تواند هنگام ساخت هر فرمانی اجرا کند و تا `DOCKRA_BUILD_TIMEOUT` از شبکه و CPU استفاده کند. حق استقرار را فقط به کسانی بدهید که با سرور به آن‌ها اعتماد دارید.
- **ساخت دیسک از یک کمک‌کار با دسترسی ویژه استفاده می‌کند** (`nsenter` به namespaceهای سرور) تا فایل‌سیستم‌های loop را بسازد.
- **برنامه‌ها به اینترنت بیرونی دسترسی دارند.** فیلتر ترافیک خروجی نداریم.
- **محدودیت نرخ فقط برای ورود است.** endpointهای دیگر احراز هویت لازم دارند ولی محدودیت نرخ ندارند؛ API را پشت Traefik بگذارید و در صورت نیاز middleware محدودیت نرخ اضافه کنید.
- **وب‌هوک‌های به سبک GitLab با `?token=`** راز را در URL می‌گذارند که ممکن است در لاگ proxyها بماند. وب‌هوک امضاشده (HMAC) را ترجیح دهید.
- **توکن داشبورد در `localStorage` است.** CSP آسیب یک باگ XSS را محدود می‌کند، ولی اسکریپت تزریق‌شده‌ای که روی مبدأ پنل اجرا شود می‌تواند آن را بخواند.
- **رمزنگاری داده‌های ذخیره‌شده** برای دیسک‌ها و بکاپ‌ها وجود ندارد (بالا را ببینید).

## چک‌لیست سخت‌سازی

- [ ] `deploy/.admin-password` را پاک کنید و برای هر مدیر و مالک 2FA را فعال کنید
- [ ] برای هر نفر یک حساب؛ ورود مشترک ممنوع
- [ ] پنل و API پشت HTTPS، با `API_BIND` و `PANEL_BIND` روی `127.0.0.1`
- [ ] وقتی HTTPS پایدار شد، `DOCKRA_HSTS_SECONDS=31536000` را تنظیم کنید
- [ ] اعضایی را که رفته‌اند غیرفعال یا حذف کنید
- [ ] `deploy/.env` با مجوز 600 و بکاپ جداگانه
- [ ] بکاپ خارج از سرور در یک bucket خصوصی
- [ ] ساعت سرور همگام (NTP)؛ TOTP به آن وابسته است
- [ ] توکن‌های بدون انقضا فقط برای CI و با نام توصیفی
